## 1. [P1] 字幕をオフにすると映像の配信まで停止する

場所: `web/app.js:3067`、`web/app.js:3114`、`internal/wui/server.go:2726`、`internal/wui/server.go:2878`。

録画済み／録画中のMP4視聴で字幕を「日本語」から「表示しない」に変更すると、
`resetPlayerSubtitleTrack()` が字幕URLへ `DELETE` を送る。
字幕と映像には同じ `session` が付くが、サーバーの停止処理はURLのリソースを区別せず、
そのトークンに属するリクエストをすべてキャンセルする。
映像のURLは設定されたままで再開処理もないため、バッファを消費した後に再生が止まる。
非MSEのライブMP4も同じ停止経路を使う。HLS映像は別管理なので、この指摘の直接の対象外。

再現: 録画済み一覧で視聴 → 再生設定 → 字幕を日本語 → 表示しない。
Playwrightでは実際の合成MP4を再生し、字幕へのDELETEが映像と同じトークンで送られ、
模擬サーバーの映像レスポンスが終了することを確認した。
加えてGoの実 `handleProgramSubtitles()` に字幕DELETEを渡し、登録済み映像リクエストの
コンテキストが `context.Canceled` になることを確認した。

修正方針: 字幕だけを止める処理と視聴セッション全体の停止を区別する。
MSEの共有セッションは維持し、字幕購読の解除だけで映像を停止しない設計にする。

## 2. [P1] HLSの1画面を閉じると同条件の別画面も停止する

場所: `internal/wui/hls.go:88`、`internal/wui/hls.go:129`、`internal/wui/hls.go:469`。

HLSの変換セッションは録画パス／チャンネル、画質、開始位置、長さ、音声で共有される。
視聴画面ごとのトークンはセッションIDに含まれない。
一方、画面終了や画質切替のDELETEは、この共有セッションを直接停止して一時ファイルも削除する。
そのため同条件で視聴している別タブ・別端末のセグメント取得も失敗する。
録画HLSでは開始位置が異なる場合は別セッションになるが、同じ初期条件で開いた画面は影響を受ける。

再現条件: Safari等のHLS経路で同じチャンネルを同じ画質の2画面で開き、一方を閉じる。
Goの実ハンドラーを使った検証では、既存セッションのセグメントが200になる状態を用意し、
別の視聴トークン付きDELETEを送ると、残った画面の同じセグメント取得が404になった。
実機Safari・実放送での同時視聴は今回実施していない。

修正方針: 共有する変換処理と各視聴者の購読を分け、終了時は当該購読だけを解除する。
変換プロセスの停止・ファイル削除は最後の購読が終了した時点で行う。

## 3. [P2] 停止要求の応答がないと再生切替と開き直しが進まない

場所: `web/app.js:2782`、`web/app.js:3581`、`web/app.js:3588`、`web/player.html:504`。

再生ソースの設定は、前のソースへのDELETEが完了するまで待つ。
停止リクエストにはクライアント側の期限がなく、画面内プレイヤーでは
`playerSourceStopPromise` に後続の停止処理も直列でつながる。
接続が応答待ちのままになると、画質切替で映像の `src` が消えた後、次の再生を開始できない。
画面を閉じて開き直しても、同じ待ち行列を使うため復旧しない。
別画面プレイヤーも停止応答待ち中は次のソースを設定できない。

再現: Playwrightで映像再生 → DELETEの応答を保留 → 画質変更 → 閉じる → 再び視聴。
開き直した後も映像の `src` が `null` のままになることを確認した。
保留していたDELETEを204で完了させると、ソースの設定が進んだ。
通常の正常応答時に発生する問題ではなく、停止経路の通信障害で発生する。

修正方針: 停止要求に期限を設け、期限到達後も待ち行列が解決するようにする。
新しい再生には別トークンを使う現在の設計を維持し、期限超過を利用者に伝える。

## 4. [P2] 再接続待ち中のtimeupdateで復旧が取り消される

場所: `web/player.html:460`、`web/player.html:591`。

別画面プレイヤーでは、受信遅延の監視とエラー後の再接続に同じ `recoveryTimer` を使う。
MSEエラーで再接続を予約しても、その後の `timeupdate` が無条件にタイマーを消す。
エラー後に残りのバッファを再生した場合などに、「自動的に再接続しています」のまま、
映像が非表示・再試行ボタンも非表示で待ち続ける。

再現: PlaywrightでMSEインターフェースをスタブ化し、エラーを通知した直後に
`timeupdate` を1回送って仮想時計を2秒進めた。プレイヤー生成回数は1回のままで、映像も非表示だった。
対照条件として `timeupdate` を送らない場合は生成回数が2回になり、再接続が実行された。
イベント順序を制御した検証であり、実放送での自然発生頻度は測定していない。

修正方針: 受信遅延監視用と再接続予約用のタイマーを分ける。
`timeupdate` は遅延監視だけを解除し、復旧予約は再生成功・明示停止・世代切替で管理する。

## 5. [P2] 正常再生中にも「再生URLが指定されていません」と表示する

場所: `web/player.html:84`。

`.message { display: grid; }` がブラウザの `hidden` 属性による非表示を上書きする。
正常なURLで再生を開始して `message.hidden = true` にしても、初期メッセージが画面下に残る。
画面内プレイヤーの `.player-status[hidden]` には対応する非表示規則があり、別画面だけに不足している。

再現: 有効な録画MP4のURLを指定して別画面プレイヤーを開く。
Playwrightで `video.currentTime > 0.1`、`message.hidden === true`、
`getComputedStyle(message).display === "grid"`、メッセージが可視であることを同時に確認した。
1440×900のスクリーンショットでも再生映像と誤メッセージの同時表示を確認した。

修正方針: `.message[hidden] { display: none; }` を追加し、正常時と失敗時の表示を検証する。
